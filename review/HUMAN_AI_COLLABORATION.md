# Record of the human-AI collaboration on the codameter GJI manuscript

Purpose: a plain record of what the author asked for and decided, and what the AI agents did in response, to support the paper's AI-assistance statement and the reviewer's author-verification pass. It records process, not competence. Dates are those of the sessions; the git history of `docs/sign-convention-manuscript` carries the exact changes.

Agents involved: Astra (Codex/GPT-6), which produced the iteration-1 review, the first revision plan, and a later "revision 2" pass; Fable (Claude, claude-fable-5-1), which audited the plan, executed the revision, and orchestrated the iteration-2 review. Earlier drafting and review sessions predate this record and are visible in the commit history (for example the v0.4.0 sign-convention work and the Copilot review of PR 37).

## Session of 2026-09-10 and 2026-09-11 (Fable)

1. **"Astra reviewed your paper; audit the plan, critique, be ready for the pre-submission reviewer."** The author asked for an independent audit of the review and its plan rather than an execution. Fable re-derived the three Fatal findings against source code and the Weaver et al. (2011) primary source, found all three correct, inventoried which figures each one reached, and critiqued the plan's ordering and its deferral of the scope decisions (`review/PLAN_AUDIT.md`).
2. **"Convert Astra's review into a JSON file for compatibility with the pre-submission agent."** Fable produced the live ledger at the path the reviewer skill reads (`reviews/codameter-gji.review.json`), preserving every finding, tier and status and adding scope and section fields; Astra's original stayed frozen.
3. **"Commit everything."** Author's instruction; Fable committed with attribution.
4. **"Do you have a plan to address Astra's issues?"** A question, answered with a phased plan and four scope decisions offered as defaults: narrow the depth-propagation claim to a described interface, describe the advisor and golden set as infrastructure without claiming an evaluation, drop the laptop-to-cloud scalability claim, and pin the external comparison script by commit.
5. **"I like the plan; write it somewhere and execute it."** The author approved the plan and its defaults. Fable executed Phases 1 to 3 (`review/EXECUTION_PLAN.md`): corrected the Weaver floor and the mixture variance, fixed the scorer, cache, shard checks, bounded-fit covariance and disconnected-epoch handling, rewired the figure build with numerical sidecars, routed the Bayesian ensemble through the canonical pipeline, made the sampler gap-aware, removed the double-counted floor, added a repeated-realisation calibration (three scenarios, 200 realisations each), recomputed the field comparison with a checked-in script, and revised the manuscript against all findings. Two findings from that work changed what the paper says: the ensemble mean's credible band under-covers the truth, and a shared source artefact is invisible to the ensemble; a clock-drift scenario turned out to cancel in the two-branch measurement and was renamed rather than presented as a shared bias.
6. **"Can you explain what 'the Gate 1 member configurations and the noisepy-dvv-cloud commit' means?"** A question. Fable found the cloud pipeline locally, explained that the field error columns had been computed with the old floor, showed that the correction is a single factor per band because every ensemble member shares the band, and identified what provenance is still missing (the run commit and use case).
7. **"Yes, apply this correction."** The author approved rescaling the archived error columns. Fable did so with an idempotent script, kept the originals, logged the factors, updated the caption and README, and switched the cloud pipeline's call to the corrected floor (left uncommitted there for the author).
8. **"/pre-submission-reviewer."** The author invoked the reviewer. Fable ran iteration 2 in reconciliation mode with ten independent subagents; a parallel Codex session had committed three further revision commits, which were reviewed as part of the current text. Verdicts: 13 resolved, 24 partially addressed, 24 introduced-in-revision entries (two Poor, both Fable's own regressions), readiness moved from "Major revision required" to "Revise before submission".
9. **"Organize the revision plan. The manuscript stays about the science. State the impact more strongly: repurposing sensors to monitor internal rheology and deformation is hard and important. Broaden the application with engineering references (concrete, wood, dam monitoring, experimental work). Add this to the review. Write down the main points of my prompts as a record of human-AI collaboration."** Fable wrote the iteration-3 plan (`review/REVISION_PLAN_ITER3.md`), added the author-requested item AUTH-01 to the ledger and report with candidate references found by web search and flagged for the author's verification (no timber and no direct dam study were found), created an author profile recording these preferences for future iterations, and wrote this record.
10. **"Should we set this up as a GitHub Action? Would the revision plan stay untouched and grounding our revision?"** A question. Fable recommended a light continuous-integration workflow only (PDF build with text checks, figure sidecar checks, the test suite), keeping the reviewer on demand because its cost and its judgement belong to a person-initiated step; and that the plan stays frozen as the grounding document except for its checkboxes and its dated log.
11. **"Sorry, I meant GitHub issues."** Fable recommended one issue per work package plus separate issues for the inputs and decisions only the author can supply, all under one milestone, so that status lives in the issues and the plan stays stable.
12. **"Yes, go for it. We will have a CLI multi-agent system tackle them; we may need to bundle them into individual PRs and have Copilot automatically review them before approval."** The author approved. Fable opened thirteen issues (#38 to #50) under the milestone "Iteration 3 revision": eight package issues P0 to P7 with ledger identifiers, acceptance criteria, file pointers and a working agreement (one pull request per issue, Copilot review requested, no hand edits to the ledger), and five author-input issues (Gate 1 provenance and rights, the Yuan et al. 2021 Table B3 ranking, the survey rows to verify, the Fig 8 decision, the step-error metric). Automatic Copilot review needs a repository ruleset that the author must enable; the repository has none.

## Decisions that were the author's

- The scope of the paper: depth propagation as an interface, the advisor as infrastructure, no cloud-scalability claim.
- The rescaling of the archived field error bars.
- The impact framing and the extension to engineering applications.
- Tracking the revision through GitHub issues with one pull request per issue and Copilot review before approval.
- Adjudication of every reviewer finding remains the author's; no finding was closed on the agent's say-so, and the iteration-2 verdicts came from independent subagents.

## What the agents did not do

They did not run external models, deploy cloud jobs, access the private golden corpus, regenerate the raw field waveforms, or deposit an archive. The three real-data figures were produced by the cloud run and are not regenerated here. Reference candidates from web searches are unverified until the author reads them.
